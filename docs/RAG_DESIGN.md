# RAG 设计说明（选型 + 参数 + 实测数字）

这份文档回答一个问题：**这套 RAG 是怎么设计的，每个参数为什么是这个值，效果有多少。**
所有数字都是本项目实测的，不是抄来的经验值；每条都给了复现命令。

配套阅读：`PROGRESS.md`（当前进度）、`HANDOFF.md`（交接与约束）、`docs/FAILURE-CASES.md`（踩坑记录）。

---

## 1. 数据：从哪来、多少条、什么格式、怎么清洗

| 项目 | 现状 |
| --- | --- |
| 来源 | `backend/corpus/` 5 篇**许可清晰**的公开资料：macrozheng/mall、mall-swarm、mall-tiny 的平台说明（Apache-2.0）、litemall 说明（MIT）、《快递暂行条例》国务院令第 697 号文本 |
| 规模 | 约 57 KB 文本 → 切分后 **74 个分块** |
| 为什么挑这些 | 演示语料会进 Git，必须能合法再分发；法规文本不受著作权保护；题材覆盖商品、订单、售后、物流、投递验收——正好是电商客服高频域 |
| 刻意避开 | 没写许可的仓库（默认保留所有权利）、GPL 等 copyleft 许可、需要登录或付费的资料 |

**支持格式与清洗规则**（`backend/app/ingestion.py`）：

- **TXT / Markdown**：按 UTF-8 解码，`errors="ignore"` 兜底；统一换行、压缩连续空白（`normalize_text`）。
- **HTML / 网页 URL**：去 `<script>/<style>` 再剥标签、`html.unescape` 反转义，只留正文。
- **PDF**：`pypdf` 逐页取文本层；`pdfplumber` 抽表格并转 Markdown 追加到正文；扫描版走可选 OCR 钩子（`OCR_ENABLED=true`，未实测）。
- **去重**：分块 id = `来源-序号-内容 sha1 前 8 位`，同一份资料重复导入只会跳过，不会重复入库（幂等）。

**还没做的**：企业自有资料（产品手册、FAQ 表格、售后政策）尚未接入；乱码 PDF 和复杂表格只做了最基础处理。

```powershell
# 复现：导入语料
powershell -ExecutionPolicy Bypass -File scripts/ingest-corpus.ps1
```

## 2. 切分：多大、重叠多少、按什么规则

参数在 `backend/app/chunking.py`：

| 模式 | 块大小 | 重叠 | 用途 |
| --- | --- | --- | --- |
| 默认（`split_text`） | 600 字 | 80 字 | 按段落优先聚合，超长段落再开滑动窗口 |
| 父子切分（`HIERARCHICAL_CHUNKING=true`） | 子块 400 字 / 父块 1200 字 | 子块间 80 字 | 子块用于检索（粒度细、命中准），父块用于生成（上下文完整） |

**为什么这么切**：

- **段落优先**：中文资料里一个自然段通常就是一个完整语义单元，按固定长度硬切会把「定制类商品除外」这类条件句切断。
- **80 字重叠**：关键条件句跨边界时，前后两个块都能命中；实测重叠再大会让索引里出现大量重复文本，检索结果里同一条反复出现。
- **父子切分**：`400/1200` 的组合让「检索粒度」和「生成上下文」解耦。代价是父块文本写进每个子块的 metadata，索引体积变大——单机小库可以接受，上千份文档就要换成独立存储。

每个分块带 `source`、`file_name`、`chunk_index`、`tenant_id`、`id`，可选 `doc_key` / `version` / `effective_from` / `effective_to`，引用与溯源都靠这些元数据。

## 3. Embedding：用哪个模型、维度多少、为什么

| 项目 | 选择 |
| --- | --- |
| 模型 | `BAAI/bge-large-zh-v1.5`（1024 维） |
| 归一化 | `normalize_embeddings=True`，检索用内积（等价余弦） |
| 运行 | CPU，权重缓存在 `models/huggingface/`，容器内离线加载（`HF_HUB_OFFLINE=1`） |

**为什么选它**：中文语义检索长期在 C-MTEB 上排名靠前；1024 维对中小知识库够用；Apache-2.0 可商用；本地 CPU 可跑，不依赖外部 embedding API，成本和数据合规都可控。

**实测代价**：CPU 上嵌入吞吐约 **142 ms/chunk**（512 条 72.6 s），模型冷加载约 **11 s**。所以工程上做了两件事——容器里把权重挂进镜像/卷避免联网校验，评测脚本预热模型把加载时间排除在计时窗口外。

## 4. 向量库：为什么是 FAISS、top-k 多少

| 项目 | 选择 |
| --- | --- |
| 实现 | `FAISSVectorStore`（`index.IndexIDMap2(IndexFlatIP(1024))`） |
| 元数据 | 与索引分开存 `records.json`（文本 + 向量 + metadata），重启可恢复 |
| 落盘 | `backend/data/faiss/`（gitignore），用 `faiss.serialize_index` 写文件 |
| top-k | 默认 **5**；检索阶段先取 `rerank_top_k=20` 再收敛到 top-k |

**为什么不是 Milvus / pgvector / Chroma**：

- **规模**：当前是单机、几十到几千分块的小库，`IndexFlatIP` 就是精确检索，没有召回损失，也不需要调参（不需要 IVF/HNSW 的 nlist/efSearch）。
- **依赖**：FAISS 是单个 Python 包，不需要额外服务；Milvus 要单独部署一套集群，pgvector 要先有 PostgreSQL——对"先跑通闭环"的阶段都是过度设计。
- **可替换**：检索层依赖 `VectorStore` 协议（`add/query/all_records/count`），换 pgvector 或 Milvus 只需要再写一个实现，`HybridRetriever` 不用改。
- **什么时候该换**：分块数到十万级以上、需要多机/多副本、或需要按租户物理隔离时，Flat 索引的线性扫描就不够了。

## 5. 检索：混合检索、rerank、阈值

**链路**：`BGE 向量检索` + `BM25 关键词检索` → 分数归一化 → 加权融合（`dense_weight=0.7`）→ 元数据过滤（租户、停用来源、生效时间、同 `doc_key` 取最高版本）→ 可选 rerank → top-k。

| 环节 | 做法 | 为什么 |
| --- | --- | --- |
| 向量检索 | FAISS 内积，取全量候选 | 语义泛化，问法和原文不一致也能命中 |
| 关键词检索 | `rank-bm25` + `jieba` 中文分词 | 药名/单号/条款号这类"字面必须一致"的查询，向量容易漂 |
| 融合权重 | 向量 0.7 / BM25 0.3 | 客服场景以语义为主，但保留关键词的精确性 |
| rerank | `BGEReranker`（CrossEncoder），代码就绪 | 精排能提升 top1 命中，代价是延迟 |
| 拒答阈值 | `RAG_MIN_SCORE=0.37`（**原始余弦**，不是归一化分） | 归一化分数永远有最大值 1.0，做不了绝对判断 |

**BM25 性能**：原实现每个候选都重算一次全量分数（O(N²)），512 条文档时循环打分 88.3 ms vs 一次性打分 0.38 ms（**233 倍**）。改成 `BM25Index.scores()` 一次算完，512 条索引检索从 370.9 ms / P95 444.3 ms 降到 **187.5 ms / 193.4 ms**。

**阈值怎么定的**（`backend/evaluation/calibrate_threshold.py`，问题集 `corpus_questions.json`）：

| 分组 | 条数 | 最高原始余弦相似度 |
| --- | --- | --- |
| 域内问题（订单/物流/售后/条例） | 10 | 最低 **0.377** |
| 域外问题（天气/股票/做菜/编程） | 8 | 最高 **0.360** |

取中点 0.369，实操用 **0.37**：域内 10/10 保留、域外 8/8 挡下（0.35 只能挡 6/8，0.42 会误伤 2 条域内）。**换语料必须重标**——同一套逻辑在示例语料上的最优值是 0.42，换到真实语料后 0.42 就偏严了。

> 注意：阈值和重排都只是"下一层保险"，不是效果来源。真正决定效果的是数据质量和切分粒度。

## 6. Prompt：怎么强制引用、怎么拒答

系统提示词（`backend/app/generation.py`）：

```text
你是企业智能客服助手。只能根据提供的知识库资料回答，不得编造。
如果资料不足，请说明无法确认，并引导用户联系人工客服。
回答要简洁、专业、友好，并尽量引用来源。
```

检索片段以 `[来源：xxx]` 前缀拼进 user prompt，模型被要求"尽量引用来源"，接口再把检索到的原文作为 `citations` 一并返回给前端——**引用不是模型说了算，而是前端展示真实召回片段**，这样引用可核对。

**拒答做成了三条路，每条都有出口**：

| 情况 | 处理 |
| --- | --- |
| 检索为空 | 建工单 + 返回带工单号的转人工话术 |
| 最高相似度低于 `RAG_MIN_SCORE` | 同上 |
| 模型读完资料自己说"资料里没有" | 生成后统一识别（`backend/app/refusal.py`），保留模型的解释，再补一句转人工 |
| 投诉 / 明确要求转人工 / 提示词注入 | 规则层直接接管，不进检索与生成 |

另外还有一层"捷径保护"：FAQ 关键词命中会零成本直接返回标准答案，但如果问题里出现**例外语**（定制、特殊、除外、生鲜、虚拟等），就不走 FAQ 改走检索——否则通用答案会盖掉知识库里的例外条款（真实踩过的坑见 `docs/FAILURE-CASES.md` 案例九）。同理，通用词（订单、客服、系统）单独命中不算 FAQ 命中。

## 7. 评估：怎么证明它好用

四套评测，全部可复现（`cd backend` 后执行）：

| 评测 | 规模 | 命令 | 实测结果 |
| --- | --- | --- | --- |
| 真实语料检索 | 5 篇 / 74 分块 / 20 条标注问题 | `python -m evaluation.corpus_eval` | doc_hit@1 **0.95**、evidence_hit@1 **0.90**、MRR **0.925** |
| 示例语料检索 | 10 条短文本 / 50 条问题 | `python -m evaluation.enterprise_eval` | hit@1 **0.96**、hit@3 1.00、MRR 0.98 |
| Agent 任务 | 150 条（订单/物流/政策/多轮/转人工/拒答注入） | `python -m evaluation.agent_eval --tag full --use-real-embedder --offline` | 成功率 **99.33%**、路由准确率 **100%**、转人工 Recall 100% / Precision 96.43% |
| 拒答阈值标定 | 10 域内 + 8 域外 | `python -m evaluation.calibrate_threshold` | 域内最低 0.377 / 域外最高 0.360 → 取 0.37 |

**两套检索口径的区别（面试常问）**：`doc_hit@k` 只看 top-k 里有没有正确的**文档**；`evidence_hit@k` 还要求命中那段里出现标注的**证据句**——后者更接近"能不能答对"。真实语料上 doc_hit@1 = 0.95 但 evidence_hit@1 = 0.90，差的那 5% 就是"文档找对了、但那一段不是答案所在"，这类失败只能靠改切分粒度或加重排解决。

**生成质量**（LLM-as-Judge，`python -m evaluation.generation_report --limit 150 --offline`）：faithfulness **1.00**、relevance **0.929**。

**压测**（`python -m evaluation.load_test --url http://127.0.0.1:8000 --concurrency 1,10,20,40,80 --requests 120`）：不调外部模型的路径并发 600 次请求**零错误**，P95 从 52.6 ms 升到 350.8 ms，吞吐在并发 20 左右饱和约 **180 RPS**。真实瓶颈是 CPU 版 BGE 检索（约 13–16 QPS）和 DeepSeek 首 token（2.5–3 s）。

## 8. 工程：流式、并发、缓存、监控、部署

| 能力 | 做法 |
| --- | --- |
| 流式输出 | `/ask/stream` 走 SSE，逐 token 推送，前端边收边渲染 |
| 并发 | FastAPI + 线程池跑阻塞工具；单实例实测 180 RPS 饱和 |
| 缓存/降本 | FAQ 命中零模型调用；命中规则、本地工具也不调模型——1928 次调用里 1910 次成本为 0 |
| 限流 | 默认 120 次/分钟/IP，超限返回 429 |
| 日志监控 | 每条问答写 JSONL（路由、模型、延迟、token、成本、引用数、trace_id）；`/metrics` 聚合；`/alerts` 按延迟与低有帮助率告警；可选 Webhook 外发 Langfuse 类平台 |
| 可观测 | 工具工作流带 `trace_id`，`GET /traces/{id}` 可回放每一步；日志写入前对手机号/邮箱/证件号/疑似 Key 脱敏 |
| 部署 | `docker compose up -d --build`：后端非 root 运行、healthcheck、模型离线加载；nginx 用 Docker DNS 动态解析后端地址 |

## 10. 已知不足

1. **rerank 未实测**：代码与 A/B 对比命令就绪（`corpus_eval --compare-rerank`），但 `bge-reranker-base` 权重 1.1GB 在镜像上限速，下载受阻。权重到位即可出数字。
2. **评测集是自己搭的**（20 + 50 + 150 条），不是业务方标注的真实分布；上线前要用真实工单采样重建。
3. **扫描版 PDF / OCR 未验证**：只有钩子。
4. **企业自有资料未接入**：现在的语料是公开替代品，换资料后必须重标阈值。
5. **单机规模**：十万分块以上要换索引结构（HNSW/IVF）和独立向量服务。

失败与排查的完整记录在 `docs/FAILURE-CASES.md`（九个案例），其中"分块 id 撞车导致分数错位"和"FAQ 吞掉例外条款"两个最值得讲。
